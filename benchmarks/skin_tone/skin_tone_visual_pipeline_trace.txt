High-level pipeline
===================

The four visuals are not produced by one report command. They come from two
pipeline stages:

Stage 1: train/evaluate models and write per-run summaries/predictions.

  scripts/run_action_bias_bench.sh
    -> benchmarks/skin_tone/build_skin_tone_shortcut_probe.py
    -> scripts/train_torchvision_rgb_probe.py for rgb_torchvision models
    -> benchmarks/skin_tone/train_skin_tone_pytorch_i3d_flow_probe.py for flow_i3d_external
    -> benchmarks/skin_tone/aggregate_skin_tone_probe.py
    -> benchmarks/skin_tone/compute_skin_tone_probe_stats.py
    -> benchmarks/skin_tone/summarize_skin_tone_robustness.py

Stage 2: run extra analysis scripts manually over stage-1 outputs.

  benchmarks/skin_tone/compare_color_jitter_conditions.py
    -> color_jitter_comparison.pdf

  benchmarks/skin_tone/analyze_skin_tone_swap_influence.py
    -> swap_pair_level_analysis.csv
    -> swap_pair_join_report.json

  benchmarks/skin_tone/summarize_skin_tone_significance.py
    -> skin_tone_variant_swap_significance_unseen.pdf

The main launcher runs the robustness plots, but it does not run the color
jitter comparison or the swap-significance analysis. That is why report
figures are currently spread over a baseline run directory and separate
analysis directories.

After cleanup, the report bundling entry point is:

  bash scripts/build_skin_tone_report.sh

It runs the existing robustness, swap-influence, significance, and color-jitter
analysis scripts, then copies canonical figures and source tables into:

  out/skin_tone_report/figures/
  out/skin_tone_report/tables/
  out/skin_tone_report/analysis/

Dataset and split generation
============================

The split manifests are generated by:

  python benchmarks/skin_tone/build_skin_tone_shortcut_probe.py ...

The launcher calls this once for each action pair and seed. The generated
files live under:

  benchmarks/skin_tone/generated/manifests/<dataset_subdir>/<pair_tag>/
  benchmarks/skin_tone/generated/labels/<dataset_subdir>/<pair_tag>_labels.csv

For the current non-smoke generated dataset:

  dataset_subdir: skin_tone_camera_far_binary
  backgrounds: autumn_hockey, konzerthaus, stadium_01
  label 0 skin variants during training/matched eval: african, indian
  label 1 skin variants during training/matched eval: white, asian
  shifted eval swaps these variant groups across labels.
  train IDs: 0, 1, 2, 3, 7, 8
  seen eval IDs: 0, 1, 2, 3, 7, 8
  unseen eval IDs: 4, 5, 6, 9

The authoritative split/count metadata is each pair's generated summary:

  benchmarks/skin_tone/generated/manifests/skin_tone_camera_far_binary/<pair_tag>/summary.json

Current generated non-smoke counts are uniform across the ten action-pair
directions:

  train_in_domain: 48 total, 24 label 0 and 24 label 1
  eval_matched_seen_ids: 48 total, 24 label 0 and 24 label 1
  eval_matched_unseen_ids: 36 total, 18 label 0 and 18 label 1
  eval_shifted_seen_ids: 48 total, 24 label 0 and 24 label 1
  eval_shifted_unseen_ids: 36 total, 18 label 0 and 18 label 1

Implementation detail after cleanup:

  build_skin_tone_shortcut_probe.py now applies --train_max_samples_per_class
  to the training split when the value is greater than 0. The launcher default
  is 0, so the existing uncapped 48-sample training split is preserved unless
  SKIN_TONE_TRAIN_MAX_SAMPLES_PER_CLASS is set explicitly.

Stage-1 output layout
=====================

The shared analysis parser is:

  benchmarks/skin_tone/aggregate_skin_tone_probe.py
    load_rows(root)

load_rows recursively scans:

  <root>/**/summary_*.json

and infers modality, model, pair_tag, seed, and eval split from the directory
layout. For rgb_torchvision it expects:

  <root>/rgb_torchvision/<model>/<pair_tag>/seed_<seed>/
    summary_rgb_<model>_model.json
    eval_matched_seen_ids/summary_rgb_<model>_model.json
    eval_matched_seen_ids/predictions_rgb_<model>.csv
    eval_matched_unseen_ids/...
    eval_shifted_seen_ids/...
    eval_shifted_unseen_ids/...

For flow_i3d_external it expects:

  <root>/flow_i3d_external/<pair_tag>/seed_<seed>/
    summary_flow_i3d_external_model.json
    eval_*/summary_flow_i3d_external_model.json
    eval_*/predictions_flow_i3d_external_model.csv

The parser silently skips summaries whose inferred mode does not match the
expected mode for the inferred modality. This keeps mixed roots usable, but it
also makes debugging missing rows harder.

Visuals 1 and 2: robustness summary and pair heatmap
====================================================

Files produced:

  skin_tone_robustness_summary_f1_macro.png
  skin_tone_pair_heatmap_f1_macro.png

Writer:

  benchmarks/skin_tone/summarize_skin_tone_robustness.py

Main command for the current baseline root:

  python benchmarks/skin_tone/summarize_skin_tone_robustness.py \
    --root out/skin_tone_probe_rgb_torchvision_v6_cj0p0 \
    --metric f1_macro

This command is also run automatically at the end of scripts/run_action_bias_bench.sh.

Call flow:

  main()
    -> load_rows(root) from aggregate_skin_tone_probe.py
    -> build_per_seed_rows(rows, metric)
    -> summarize_modalities(per_seed_rows, metric)
    -> summarize_pairs(per_seed_rows, metric)
    -> write_csv/write_json for model-level robustness summary
    -> write_pair_csv/write_pair_json for pair-level robustness summary
    -> write_plot(...) creates skin_tone_robustness_summary_<metric>.png/pdf/svg
    -> write_pair_heatmap(...) creates skin_tone_pair_heatmap_<metric>.png/pdf/svg

Inputs:

  All per-split and per-run summary_*.json files below the root. The script
  does not read prediction CSVs.

Unit of aggregation:

  A unit is pair_tag x modality/model x seed after the four eval splits have
  been folded into one row by build_per_seed_rows().

Metrics computed:

  matched_seen_ids = metric on eval_matched_seen_ids
  shifted_seen_ids = metric on eval_shifted_seen_ids
  matched_unseen_ids = metric on eval_matched_unseen_ids
  shifted_unseen_ids = metric on eval_shifted_unseen_ids
  drop_training_videos = matched_seen_ids - shifted_seen_ids
  drop_testing_videos = matched_unseen_ids - shifted_unseen_ids

skin_tone_robustness_summary_f1_macro.png:

  A two-panel scatter/errorbar figure. Each point is a model/modality averaged
  across its pair x seed units. The x-axis is matched minus shifted F1. A value
  near 0 means the model is insensitive to the skin-tone swap under that split.
  The y-axis is shifted F1. The left panel uses seen IDs, and the right panel
  uses unseen IDs.

skin_tone_pair_heatmap_f1_macro.png:

  A two-panel heatmap over model x action pair. Values are the same matched
  minus shifted F1 drops, aggregated across seeds for each model and pair.
  The first panel is seen/training-ID sensitivity; the second is unseen/test-ID
  sensitivity.

Visual 3: color-jitter comparison
=================================

File produced:

  color_jitter_comparison.pdf

Writer:

  benchmarks/skin_tone/compare_color_jitter_conditions.py

The per-condition roots are produced by:

  bash scripts/run_skin_tone_color_jitter_sweep.sh

That sweep forces:

  MODALITIES=rgb_torchvision
  SKIN_TONE_MODALITIES=rgb_torchvision
  SKIN_TONE_COLOR_JITTER=<value>
  SKIN_TONE_OUT_ROOT=<base>_cj<value-with-dot-as-p>

Example comparison command matching the current report artifact:

  python benchmarks/skin_tone/compare_color_jitter_conditions.py \
    --roots \
      cj0p0=out/skin_tone_probe_rgb_torchvision_v6_cj0p0 \
      cj0p4=out/skin_tone_probe_rgb_torchvision_v6_cj0p4 \
      cj0p8=out/skin_tone_probe_rgb_torchvision_v6_cj0p8 \
    --metric f1_macro \
    --out_dir out/skin_tone_probe_rgb_torchvision_v6_analysis/color_jitter_v2

Call flow:

  main()
    -> parse_root_specs(...)
    -> infer_condition_value(...) sorts cj0p0, cj0p4, cj0p8 numerically
    -> summarize_condition(...) for each root
         -> load_rows(root)
         -> build_per_seed_rows(...)
         -> keep only modality values starting with rgb_torchvision:
         -> optionally read root/swap_pair_level_analysis.csv for pred_flip rates
    -> build_robustness_rows(...) compares each non-baseline condition to the first root
    -> write color_jitter_comparison.csv/json
    -> plot_condition_comparison_bars(...) writes color_jitter_comparison.pdf
    -> write color_jitter_robustness_checks.csv/json
    -> collect_pair_sensitivity(...) and plot_pair_heatmap(...) write color_jitter_pair_heatmap.pdf

Inputs:

  Per-split/per-run summary_*.json files from each condition root.
  Optional: swap_pair_level_analysis.csv in each condition root for prediction
  flip rates. If missing, pred_flip columns become NaN but the PDF still builds.

Unit of aggregation:

  For each color-jitter condition and model, the script averages across
  pair_tag x seed units. For the current JSON this is 30 units per model:
  10 action-pair directions x 3 seeds.

Meaning of color_jitter_comparison.pdf:

  Horizontal grouped bars compare mean swap-drop F1 across jitter levels.
  The two panels are seen-ID and unseen-ID swap drops. Lower is better because
  the value is matched minus shifted F1.

Visual 4: variant-swap significance heatmap
===========================================

File produced:

  skin_tone_variant_swap_significance_unseen.pdf

This visual has a required precursor file:

  swap_pair_level_analysis.csv

Precursor writer:

  benchmarks/skin_tone/analyze_skin_tone_swap_influence.py

Current precursor command for the combined analysis root:

  python benchmarks/skin_tone/analyze_skin_tone_swap_influence.py \
    --root out/skin_tone_probe_rgb_torchvision_v6_cj0p0 \
    --metric f1_macro \
    --out_dir out/skin_tone_probe_rgb_torchvision_v6_analysis_combined

analyze_skin_tone_swap_influence.py call flow:

  main()
    -> load_prediction_rows(root, models_filter)
         -> scans root/rgb_torchvision/**/predictions_rgb_*.csv
         -> scans root/flow_i3d_external/**/predictions_flow_i3d_external_model.csv
         -> normalizes model, pair_tag, seed, eval_split, background, action,
            base_id, variant, tone_group, logits/probability-derived columns
    -> build_pair_rows(...)
         -> for each model x pair_tag x seed x split_family:
              seen: eval_matched_seen_ids vs eval_shifted_seen_ids
              unseen: eval_matched_unseen_ids vs eval_shifted_unseen_ids
         -> pairs samples by background, action, base_id, and mapped variant
         -> variant map: african<->white, indian<->asian
         -> writes correctness and prediction-flip deltas per pair
    -> compute_feature_ranking(...)
    -> write swap_pair_level_analysis.csv
    -> write swap_pair_join_report.json
    -> write swap_influence_feature_ranking.csv/json
    -> write swap_influence_features.pdf and swap_flip_rate_breakdowns.pdf

The current combined join report says:

  source root: out/skin_tone_probe_rgb_torchvision_v6_cj0p0
  prediction_csv_count: 840
  prediction_row_count: 35280
  pair_row_count: 12600

Final significance writer:

  benchmarks/skin_tone/summarize_skin_tone_significance.py

Command matching the current unseen PDF:

  python benchmarks/skin_tone/summarize_skin_tone_significance.py \
    --root out/skin_tone_probe_rgb_torchvision_v6_analysis_combined \
    --metric_roots \
      cj0p0=out/skin_tone_probe_rgb_torchvision_v6_cj0p0 \
      cj0p4=out/skin_tone_probe_rgb_torchvision_v6_cj0p4 \
      cj0p8=out/skin_tone_probe_rgb_torchvision_v6_cj0p8 \
    --metric f1_macro \
    --split_family unseen

Call flow:

  main()
    -> parse_root_specs(metric_roots, root)
    -> compute_model_significance_rows(metric_roots, metric)
         -> uses load_rows(root) to compute matched-vs-shifted paired tests
            and condition-drop comparisons for CSV/JSON/MD outputs
    -> load root/swap_pair_level_analysis.csv
    -> compute_variant_significance_rows(pair_rows, split_family)
         -> group by model, variant_matched, variant_shifted
         -> compute matched accuracy, shifted accuracy, accuracy_drop
         -> McNemar exact test from discordant correctness counts
         -> Bonferroni-adjust p-values within each model
    -> write skin_tone_variant_swap_significance_<split_family>.csv/json
    -> write skin_tone_significance_summary.csv/json/md
    -> plot_variant_heatmaps(...) writes skin_tone_variant_swap_significance_<split_family>.pdf

Meaning of skin_tone_variant_swap_significance_unseen.pdf:

  Two heatmaps over model x directional skin-tone swap. The top heatmap shows
  raw McNemar p-values; the lower heatmap shows Bonferroni-adjusted p-values.
  Each cell tests whether matched and shifted correctness differs for a
  specific directional variant swap on unseen-ID paired samples.

Where the prediction CSVs come from
===================================

RGB torchvision:

  scripts/train_torchvision_rgb_probe.py eval writes:

    eval_*/predictions_rgb_<model>.csv
    eval_*/summary_rgb_<model>_model.json

  The eval parser defaults export_predictions=True and export_clip_stats=True.
  Therefore predictions are written even when the launcher passes
  --summary_only. In this script, summary_only only suppresses confusion and
  per-class metric files.

Flow I3D:

  benchmarks/skin_tone/train_skin_tone_pytorch_i3d_flow_probe.py eval writes:

    eval_*/predictions_flow_i3d_external_model.csv
    eval_*/summary_flow_i3d_external_model.json

  It always writes predictions. summary_only suppresses extra confusion and
  per-class files, not predictions.

Explainability/code-structure review
====================================

What is understandable:

  The individual scripts are mostly readable once opened directly. Their CLIs
  have argparse help, and most scripts write source tables next to figures.
  The output names are descriptive, and the main first-stage launcher prints
  the exact commands it runs. The generated manifest summary JSONs preserve
  split counts, chosen IDs, missing files, and notes.

Main problems:

  1. There is no single report pipeline entry point.

     The baseline robustness figures are created by the main launcher, while
     color-jitter comparison and variant significance are manual second-stage
     calls. That is the main reason the four report figures feel disorderly.

  2. The central data model is implicit.

     aggregate_skin_tone_probe.load_rows() infers meaning from directory
     paths and JSON shape. Several scripts then repeat their own
     build_per_seed_rows(), mean/std helpers, split names, model display names,
     color maps, and variant constants. This makes it harder to explain what
     a "unit" means and increases the chance that two figures aggregate
     slightly differently.

  3. The directory-layout dependency is silent.

     load_rows() silently skips summary files if parse_summary_location()
     cannot infer modality/pair/seed/split or if the inferred mode does not
     match. This behavior is convenient for mixed roots, but it hides missing
     or malformed inputs during reproduction.

  4. summary_only is misleading.

     In both RGB torchvision and flow eval paths, prediction CSVs are still
     written under summary_only. This matters because the significance figure
     depends on those prediction CSVs. The name suggests less output than it
     actually produces.

  5. analyze_skin_tone_swap_influence.py is doing too much.

     It contains path parsing, variant parsing, prediction loading,
     matched/shifted sample pairing, statistical feature ranking, CSV writing,
     and plotting. It is understandable in sections, but it is long enough
     that the key explainability step, the paired sample join, is buried.

  6. Variant parsing and skin-tone constants are duplicated.

     The same ideas appear in build_skin_tone_shortcut_probe.py,
     train_torchvision_rgb_probe.py, train_skin_tone_pytorch_i3d_flow_probe.py,
     analyze_skin_tone_swap_influence.py, and summarize_skin_tone_significance.py.
     That is risky because report interpretation depends on identical variant
     semantics across training, prediction export, pairing, and plotting.

  7. Some reproducibility seeds used Python hash().

     This has been moved to a stable SHA-based helper in schema.py for the
     color-jitter and significance bootstrap paths.

  8. The train sample cap option appeared unused.

     This has been fixed by preserving the uncapped default and honoring an
     explicit positive cap.

  9. Optional dependencies are not explicit in the figure commands.

     compare_color_jitter_conditions.py optionally reads swap_pair_level_analysis.csv
     for prediction flip rates. If the file is missing, the figure still builds
     with NaNs in those columns. That is acceptable behavior, but the script
     should say so in its output or documentation.

Recommended changes
===================

1. Add a documented report entry point. Done.

   The entry point is:

     scripts/build_skin_tone_report.sh

   It should run, in order:

     summarize_skin_tone_robustness.py for the baseline root
     analyze_skin_tone_swap_influence.py for the baseline root
     summarize_skin_tone_significance.py for the analysis root
     compare_color_jitter_conditions.py for all jitter roots

   It writes a single report directory, by default:

     out/skin_tone_report/
       figures/
       tables/
       analysis/
       README.txt

   The current run directories can remain untouched as raw outputs.

2. Move shared benchmark semantics into one module. Partially done.

   A small shared module now exists:

     benchmarks/skin_tone/schema.py

   It defines the split names, split-family mapping, skin-tone variant groups,
   variant swap mapping, model colors, and stable_seed(). More constants can
   be moved there as future cleanup.

   Then import those constants everywhere instead of redefining them.

3. Split data collection from plotting.

   Keep plotting scripts thin. Put reusable transformations in modules with
   names that explain the data contract, for example:

     collect_eval_rows(root) -> list[EvalSplitRow]
     fold_eval_splits(rows) -> list[ProbeUnit]
     pair_matched_shifted_predictions(root) -> list[SwapPairRow]

   Then plotting scripts become easier to audit:

     rows = collect...
     table = summarize...
     plot(table)

4. Make load_rows noisy in a controlled way. Partially done.

   aggregate_skin_tone_probe.py now exposes load_rows_with_report(root), which
   returns rows plus counts/lists for scanned, accepted, parse-skipped,
   mode-mismatched, and duplicate summary files. Existing load_rows(root)
   remains compatible.

   Future CLI output could print:

     number of summary files scanned
     number accepted
     number skipped by parse failure
     number skipped by mode mismatch
     missing required splits per unit

   This would make reproduction failures much easier to diagnose.

5. Replace hash-based bootstrap seeds. Done for the traced paths.

   The color-jitter and significance scripts now use schema.stable_seed().

6. Fix or remove train_max_samples_per_class. Done.

   The generator now honors an explicit positive train cap, while the launcher
   default is 0 to preserve the current uncapped training split by default.

7. Normalize output formats.

   Give each plotting script:

     --out_dir
     --formats pdf,png,svg

   Baseline robustness currently writes png/pdf/svg, while color-jitter and
   significance write PDF only. A report builder can copy or symlink canonical
   formats into one figures directory.

8. Add small fixture tests.

   Useful tests would cover:

     load_rows() against a tiny nested output tree
     build_per_seed_rows() drop calculations
     build_pair_rows() matched/shifted join behavior, including missing pairs
     summarize_skin_tone_significance.py McNemar counts on a tiny CSV
     each visual CLI as a smoke test with fixture data

Bottom line
===========

The current scripts are usable and locally understandable, but the pipeline is
hard to explain end-to-end because the call graph is split between launcher
steps and manual second-stage analysis, while data contracts are encoded in
path conventions and repeated helper logic. The first cleanup should not be a
large rewrite. Start by adding a report builder, centralizing constants/schema,
making load_rows report what it accepted/skipped, and fixing the train sample
cap ambiguity.
